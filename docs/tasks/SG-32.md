# SG-32 — Preparação para Implantação e Operação

## Situação anterior e riscos

- ASP.NET Core 8 e React/Vite já tinham comandos locais e configuração SQL Server.
- O backend não aplicava migrations automaticamente, porém executava `DbSeed.InitializeAsync` toda vez que iniciava. Isso podia criar roles e turnos e, quando `Seed:AdminEmail`/`Seed:AdminPassword` estavam definidos, provisionar Admin.
- O health endpoint existente (`/api/health`) indicava apenas que o processo respondia.
- O frontend chama `/api` na mesma origem; `VITE_API_TARGET` é proxy apenas do Vite em desenvolvimento.
- Hospedagem, domínio, TLS, proxy, banco institucional, CORS, primeiro Admin, IdP e política operacional ainda não estão definidos.

## Alterações

- O seed agora exige `Bootstrap:EnableDevelopmentSeed=true` e só pode executar quando `IHostEnvironment` é Development. A opção é opt-in no perfil local `SalaGest.Api` de `launchSettings.json`; sem essa opção não há consulta nem gravação do seed. Staging/Production falham com mensagem de configuração se a opção estiver ligada. O conteúdo e as regras já existentes de `DbSeed` foram preservados.
- A aplicação continua sem aplicar migrations durante o startup. A configuração SQL Server com `TrustServerCertificate=true` agora falha fora de Development; a connection string aprovada deve validar o certificado.
- Foi preservado `/api/health`; adicionados `/health/live` (processo) e `/health/ready` (conectividade SQL Server via `CanConnectAsync`, sem gravação). A resposta de prontidão é genérica e retorna 503 em falha.
- Exceções não tratadas em ambientes não Development passam pelo tratamento padrão Problem Details, sem stack trace na resposta; o middleware mantém o logging da exceção no servidor.
- Não houve alteração do modelo EF, connection string, `Backend/appsettings.json`, autenticação, permissões ou política CORS.

## Configuração, build e operação

O guia `docs/deployment/README.md` documenta variáveis ASP.NET Core, User Secrets local, permissões SQL separadas para runtime e manutenção, build/publish, mesmo-origin/proxy `/api`, HTTPS/CORS, OIDC, migrations revisadas, health checks, backup existente, atualização e rollback. Não foi escolhida uma hospedagem (IIS, serviço ou proxy) porque a infraestrutura institucional não foi confirmada.

O checklist `docs/deployment/checklist.md` prepara instalação e verificações posteriores na SG-30. Foram reutilizados os scripts `tools/backup/backup-sqlserver.ps1`, `tools/backup/restore-sqlserver-isolated.ps1` e a documentação SG-29; nenhum script operacional novo foi criado ou executado.

## Migrations e banco

Nenhuma migration necessária ou criada. Não foi executada consulta ao SQL Server, `database update`, seed, backup, restore ou início da API. O estado de aplicação das migrations no banco de casa continua não confirmado. O guia descreve `dotnet ef migrations list` (consulta somente leitura ao banco após conferir o destino) e geração/revisão de SQL separado; nenhum SQL foi aplicado.

## Testes e verificações

- Criados testes unitários da política de seed: desativado por padrão e bloqueado fora de Development.
- `dotnet build Backend/SalaGest.Api.csproj --no-restore`: passou, zero erros/avisos no projeto da API. A tentativa normal de build/restore não conseguiu acessar NuGet (`NU1301`) por restrição de rede do ambiente.
- `dotnet test ... --no-restore --filter FullyQualifiedName~DbSeedStartupTests`: 3 aprovados; a compilação dos testes mostrou 2 avisos nullable preexistentes em `TeachingAssignmentTests.cs` e `OccupationMoveTests.cs`.
- `npm.cmd run build` em `Frontend`: passou (`tsc -b` e Vite production build). O shim `npm.ps1` foi bloqueado pela Execution Policy do PowerShell; usar `npm.cmd` funcionou sem alterar política do sistema.
- `git diff --check`: passou; Git avisou apenas sobre normalização LF/CRLF no documento SG-29 reutilizado.
- Sem homologação, testes de rede, teste real de health check, SQL Server, migração, backup, restauração ou carga.

## Pendências de infraestrutura/instituição

- Host, sistema operacional, domínio, TLS, proxy confiável, porta e roteamento.
- SQL Server de Staging/Production, identidade da aplicação e processo DBA para migrations.
- Provisionamento seguro do primeiro Admin, sem credenciais padrão.
- CORS e parâmetros do provedor SSO real; Data Protection/afinidade se múltiplas instâncias.
- Política de backup: frequência, retenção, destino, criptografia/custódia, RPO, RTO e responsáveis.
- Valores institucionais e decisões D-01, D-03, D-04, D-06, D-08.
- À época da SG-32, a movimentação de blocos RN-07/RN-08 estava pendente. O complemento posterior da SG-18 a implementou por formulário; a homologação integrada e a avaliação da diferença visual sem arrastar e soltar continuam pendentes.

## Limitações e SG-30

Readiness apenas verifica se o banco aceita conexão; não valida schema, estado de migrations ou funcionalidades. O endpoint não deve ser tratado como diagnóstico detalhado. Configuração de HTTPS/forwarded headers é responsabilidade da topologia aprovada; confiar em proxy sem lista confiável foi evitado.

A SG-30 deverá validar em ambiente isolado: inicialização sem alterações; SQL e migrations; health e indisponibilidade; autenticação e perfis; fluxos SG-07–29/31; logs/privacidade; import/export; backup e restauração real isolada; atualização/rollback; desempenho; responsividade e acessibilidade. Consulte `docs/deployment/checklist.md`.
